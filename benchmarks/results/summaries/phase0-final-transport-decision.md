# AlphaX Phase 0 final transport decision experiment

Date: 2026-08-14
Status: final planned Phase 0 evidence round; maintainer review required
Production transport: not selected; ADR 0004 intentionally not created
C++ engine: not used

This report records the final targeted experiment requested for Phase 0. It is an
evidence-based recommendation for review, not an accepted production
architecture decision. AlphaX remains transport-independent and Phase 1 has not
started.

## 1. Executive summary

The experiment used a controlled Linux Docker topology with TLS, explicit ALPN
verification, and symmetric tc/netem shaping. The selected evidence set
contains 33 raw machine-readable result files, 33 generated summary JSON files,
33 Markdown summaries, and 3,934 retained samples. The 100 MB transfer samples
that completed contain 50 validated downloads and 50 validated uploads; every
included transfer has the expected byte count and FNV-1a64 hash.

The evidence supports Dart IO as the lowest-risk Phase 0 direction. Native
prototypes show useful capabilities—especially HTTP/2 multiplexing and direct
native-to-file paths—but the final experiment does not show a sufficiently
consistent, practically meaningful advantage to pay the FFI, packaging, build,
debugging, and security-update costs. The current Rust HTTP/2 path also has a
reproducible poor-network stream/concurrency correctness failure, so its
performance is not eligible for a complete final comparison under that profile.

The recommendation below does not modify alphax, alphax_native, or any
production transport architecture.

## 3. Network shaping methodology

The same profile was applied to both endpoint interfaces. The one-way delay is
therefore approximately half the target RTT at each endpoint before bridge and
processing overhead.

| Profile | tc netem delay per endpoint | Approx. RTT | Rate per endpoint | Loss | Seed |
| --- | ---: | ---: | ---: | ---: | ---: |
| Local/control | no qdisc | no impairment | unlimited | 0% | n/a |
| Good | 15 ms | ~30 ms | 100 Mbit/s | 0% | 1001 |
| Typical mobile | 50 ms | ~100 ms | 10 Mbit/s | 0.5% | 2001 |
| Poor mobile | 150 ms | ~300 ms | 5 Mbit/s | 2% | 3001 |

The effective commands were equivalent to:

~~~text
tc qdisc replace dev eth0 root netem delay 15ms loss 0% rate 100mbit limit 10000 seed 1001
tc qdisc replace dev eth0 root netem delay 50ms loss 0.5% rate 10mbit limit 10000 seed 2001
tc qdisc replace dev eth0 root netem delay 150ms loss 2% rate 5mbit limit 10000 seed 3001
tc qdisc del dev eth0 root
~~~

The exact profile implementation is in
benchmarks/scripts/network-profile-linux.sh. Deterministic seeds were added
so the independently executed native candidates do not inherit a different
packet-loss sequence from one another. run-linux-final-decision.sh reapplies
the same profile before each H2 candidate and always resets it during cleanup.

## 4. TLS and HTTP/2 verification

- A benchmark-specific local CA and server certificate are generated by
  benchmarks/scripts/create-local-tls.sh.
- Candidates trust that CA through ALPHAX_BENCHMARK_CA_CERT; certificate
  verification remains enabled.
- No insecure flag, disabled verification, or trust-all callback was used.
- The H2 server advertises h2 through ALPN and the readiness check uses
  openssl s_client -alpn h2,http/1.1.
- Included H2 samples have server-observed protocol 2; the integrity check
  found zero H2 samples that fell back to HTTP/1.1.
- Dart IO is recorded over verified TLS HTTP/1.1 because the current Dart
  prototype does not negotiate HTTP/2. It is not silently presented as an H2
  candidate.

## 5. Scenario and statistical methodology

The final run was intentionally limited to the decision-sensitive scenarios:

- 1 KB cold and warm request;
- 100 sequential small requests;
- 50, 100, and 250 concurrent small requests;
- 2 MB normal, slow-consumer, and paused-consumer streams;
- 100 MB download and upload;
- 100 MB direct native-file download and upload for native candidates.

Request and concurrency scenarios use 30 measured samples after warmup where
the candidate/profile completed correctly. Stream and transfer scenarios use
the available profile-specific repetitions: 10 local stream samples, 5 good
network samples, 3 typical-mobile samples, 2 poor-mobile samples, and 2–5
transfer samples. p99 is not used for samples below 20. Raw samples are retained
and each generated summary reports min, mean, p90, p95, max, and standard
deviation when those values are meaningful.

Timing boundaries are shared:

- request timing begins before request creation;
- upload timing begins before file length/stat preparation;
- upload timing ends after the response body and native cleanup notification;
- download timing ends after the file sink closes;
- concurrency timing begins before the first future is created and ends after
  all futures complete.

The runner keeps JSON decoding out of transport samples. Uploads and downloads
are validated against deterministic bytes and FNV-1a64 hashes.

### Practical-equivalence rule

The runner’s statistical labels remain:

- approximately equivalent: p50 difference <=5%;
- likely difference: >=10% with acceptable variance;
- clear difference: >=20%, non-overlapping p25–p75, and <=10% coefficient of
  variation;
- otherwise inconclusive.

For shaped-network interpretation, a small-request difference of <=10 ms or
<=5% under a profile whose RTT is at least 30 ms is treated as practically
equivalent unless it is accompanied by a material CPU, RSS, correctness, or
connection-efficiency advantage. A large-transfer difference from fewer than 20
samples is directional only and is not treated as a stable winner.

### Rust poor-network H2 limitation

The Rust candidate completed a valid poor-profile H2 request subset and that
raw file is retained. Separate deterministic probes and the continuation of the
poor-profile run reproduced response-stream failures at high concurrency and
while streaming, including UnexpectedEof, connection reset, and broken-pipe
failures. The runner correctly refused to write a complete comparable stream
dataset after the failure. No Rust poor-profile H2 stream or transfer result is
used as a performance claim.

This is a correctness result, not a performance penalty assigned to Rust. It
means the current Rust prototype is not decision-ready for the complete poor
network H2 workload.

## 9. Connection behavior

### Persistent libcurl engine

The libcurl prototype now uses one persistent client worker and one persistent
CURLM multi handle. Easy handles are added to that multi handle for individual
requests. The worker uses readiness-driven curl_multi_poll; curl_multi_wakeup
interrupts the worker for new work and cancellation. Shutdown drains/cancels
easy handles, wakes the worker, joins it, and cleans up the shared state.

HTTP/2 required an additional correctness fix. Negotiating ALPN h2 alone did
not cause concurrent easy handles to multiplex. The prototype now enables:

~~~c
curl_multi_setopt(multi, CURLMOPT_PIPELINING, CURLPIPE_MULTIPLEX);
curl_easy_setopt(easy, CURLOPT_PIPEWAIT, 1L);
~~~

Before this fix, a 250-request H2 run opened roughly 150 connections and could
fail with HTTP/2/TLS errors. After the fix, the deterministic poor-profile run
opened three connections and completed all 250 libcurl requests.

### Observed reuse

| Workload | Dart IO H1 | libcurl H1 | Rust H1 | libcurl H2 | Rust H2 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 sequential requests, local/good/typical | 1–2 | 1 | 1 | 1 | 1 |
| 100 sequential requests, poor | 1–3 | 1 | 1 | 1 | 1 |
| 250 concurrent requests, local | ~250 | ~239–250 | ~127–250 | 3 | 1 |
| 250 concurrent requests, good | 250 | 250 | 250 | 3 | 1 |
| 250 concurrent requests, typical | 250 | 250 | 250 | 3 | 1 |
| 250 concurrent requests, poor | 250 | 250 | 250 | 3 | 1 in valid request subset |

HTTP/1.1 concurrency naturally requires more connections. The important
acceptance criterion—connections far below requests for 100 sequential
requests—now passes for libcurl. Connection counts come from server-observed
remote ports/connection IDs, not latency inference.

## 10. Bounded backpressure and FFI behavior

The native streaming baseline remains:

~~~text
64 KiB chunk × 4 credits = 256 KiB logical native window
~~~

The credit/acknowledgement flow is bounded: Dart grants credits, native emits
no more than the available credits, and native stops response delivery when the
window is exhausted. Dart acknowledgements restore credits. Cancellation while
paused wakes the native worker and releases the handle.

The final data records 32 FFI notifications for a 2 MB stream in the normal
native paths. Observed maximum buffered values are approximately 256 KiB for
libcurl and up to 320 KiB for Rust, where one upstream native chunk can remain
in flight in addition to the four-chunk window. This is bounded behavior, not
uncontrolled buffering.

Round 3/4 backpressure measurements also remain valid: fast, slow, and paused
consumers complete correctly; pause/resume and cancellation release native
resources. Rust’s poor H2 correctness failure means its poor-profile stream
performance is excluded even though its normal-profile bounded queue remains
observable.

The direct-file paths are explicitly recorded as:

~~~text
Dart:   network → Dart stream → file
native: network → native transport → file
~~~

The native path can avoid delivering every file byte through Dart, but the
benchmark does not call that zero-copy.

## 11. CPU and RSS measurements

The runner captured process-level CPU time, CPU utilization, current RSS, and a
10 ms sampled peak RSS. It did not claim Dart/native allocation separation.

The Linux container’s ps CPU time has coarse approximately one-second
resolution. Consequently, many short-request CPU deltas are recorded as zero
or one second and are not reliable enough to rank close candidates. RSS is
process-level and includes the Dart VM, benchmark runner, loaded native library,
and allocator state. ProcessInfo.maxRss is cumulative; the sampled peak is the
more useful per-operation field. All raw values remain available.

Representative local H1 observations are below; CPU values are cumulative
process CPU seconds and RSS is sampled peak increment over the operation’s
before measurement:

| Scenario | Candidate | CPU p50 (s) | Sampled peak RSS delta p50 |
| --- | --- | ---: | ---: |
| 250 concurrent | Dart IO | 0 | 124 KiB |
| 250 concurrent | libcurl FFI | 0 | 1.54 MiB |
| 250 concurrent | Rust FFI | 0 | 6.32 MiB |
| 100 MB download | Dart IO | 3 | 20 KiB |
| 100 MB download | libcurl FFI | 1 | 0 KiB |
| 100 MB download | Rust FFI | 3 | 16 KiB |
| Slow 2 MB stream | Dart IO | 0 | 0 KiB |
| Slow 2 MB stream | libcurl FFI | 0 | 4.54 MiB |

These measurements do not demonstrate a stable native CPU or memory win. The
Rust concurrency RSS signal is directionally higher in the captured process;
the short-run CPU measurement is not precise enough for a final ranking. A
future production implementation would need isolated per-candidate processes
and platform-specific counters before making a finer-grained resource claim.

The measurement script builds release Dart AOT benchmark executables and strips
native libraries. Linux dependency extraction records ELF DT_NEEDED entries;

zlib, brotli, zstd, IDN, SSH, PSL, LDAP/Kerberos, and related libraries. Those

## 15. Remaining limitations and risks

1. The Linux experiment used an arm64 Docker VM, not native Linux x64 or mobile
   hardware.
2. Dart H2 was not available in the current prototype, so H2 native results
   are not a three-way protocol comparison.
3. Rust poor-network H2 stream/concurrency correctness is unresolved. This is
   the largest residual native risk, but it does not justify another broad
   Phase 0 matrix in this report.
4. Rust H2 local/good/typical successful files include the earlier successful
   run before deterministic packet-loss reset was added; their provenance and
   raw metadata are retained, and the corrected libcurl reruns are separate.
5. Transfer repetitions are intentionally small because 100 MB transfers under
   the poor profile are very expensive. Their medians are directional.
6. CPU counters in the container are too coarse for close short-request
   comparisons. RSS is process-level and cannot split Dart/native allocations.
7. Nitro and Dio are external references from earlier rounds, not candidates in
   this final controlled matrix. No unfair or incomparable result is presented
   as a final candidate measurement.
8. HTTP/3 was not benchmarked. No candidate receives credit or penalty for an
   unimplemented H3 path.
9. The macOS and Linux native artifact values are harness measurements. Android
   and iOS artifact sizes remain unbuilt estimates/packaging implications.

## 16. Recommendation rationale

### Why Dart IO wins overall

- It is the only candidate with no native ABI, native runtime, per-ABI binary,
  or cross-language lifecycle burden.
- It completed the shaped HTTP/1.1 correctness matrix, including poor-network
  250-concurrency, streaming, and validated 100 MB transfers.
- Under good, typical, and poor RTT profiles, 1 KB warm request differences are
  practically equivalent. Local native wins are not sufficient evidence of
  user-visible benefit.
- Good-network 100 MB transfer results are practically equivalent because the
  network profile dominates. Native direct-file paths are useful hypotheses,
  but the measured advantage is not consistent enough to justify shipping a
  second runtime.
- The public AlphaX value can still come from a transport-neutral API, policy,
  resilience, observability, testing, and future direct-file abstractions
  without selecting a native engine now.

### What Dart IO loses

- The current prototype does not provide HTTP/2 or HTTP/3 comparison coverage.
- It does not provide the native direct-to-file path demonstrated by the two
  native candidates.
- On localhost, Rust and sometimes libcurl have lower small-request or
  concurrency latency; those measurements do not survive as a material,
  consistent advantage under shaped RTT in this evidence set.

### Cost and risk tradeoff

Choosing Dart IO avoids the libcurl system/bundling graph and the Rust
multi-megabyte payload, keeps the package pure Dart, and reduces build/CI and
security-update surfaces. The cost is that any future H2/H3 or direct-file
requirement must be demonstrated as a real product need rather than assumed
from localhost microbenchmarks.

### HTTP/3 path

HTTP/3 was not part of this decision experiment. If a product requirement makes
it important, AlphaX should first measure the actual Dart/platform capability
against a separately justified native path. A curl or Rust H3 feature flag
alone is not sufficient evidence for adding a native runtime.

### Conditions for revisiting

Revisit this recommendation only if a focused follow-up demonstrates a material
user-visible benefit that Dart IO cannot reasonably provide, such as:

- verified production H2/H3 capability required across target platforms;
- a stable, correctness-complete native direct-file advantage with meaningful
  CPU/RSS reduction;
- a corrected Rust loss/H2 implementation with a clear benefit after complete
  mobile-target artifact accounting; or
- a platform-specific capability gap that cannot be addressed behind the
  transport-neutral AlphaX contract.

Any revisit requires a new evidence record and maintainer review before ADR
0004. No production transport is selected by this report.
