# AlphaX 1.0 security and platform-transport research

**Status:** Research-only note; no production behavior is changed by this file.
**Reviewed:** 2026-08-15
**Scope:** Minimum technically honest mappings for the Dart `dart:io` fallback, Android Cronet/`HttpEngine`, and Apple `URLSession`/Security adapters.

This note uses the public official API documentation linked below. “Supported” means that the adapter can enforce the requested policy with the documented API, not merely express a preference. A capability that can only be checked after a request has been sent is not a safe implementation of a hard requirement for an unsafe mutation.

## Executive conclusions

- Platform trust is the safe baseline on all three platforms. Custom trust anchors are materially different: Dart supports a per-`HttpClient` `SecurityContext`; Apple supports per-challenge `SecTrust` changes; Android exposes static app/domain Network Security Configuration, but the public Cronet/`HttpEngine` builders do not expose a runtime trust-anchor setter.
- Cronet/`HttpEngine` has first-class SPKI SHA-256 pinning. Apple can implement public-key pinning in a server-trust challenge, but there is no one-call URLSession pin policy and exact Cronet-compatible SPKI hashing requires DER `SubjectPublicKeyInfo` serialization. Dart `dart:io` has no first-class SPKI policy or public-key accessor.
- Dart and Apple expose client-certificate/mTLS hooks. The public Cronet/`HttpEngine` request API does not expose a client-certificate callback or identity setter, so mTLS must be reported unsupported by the Cronet adapter unless a selected provider adds a separately verified extension.
- Proxy behavior is not portable. Dart’s documented default is environment-based proxy selection; Cronet uses system proxy configuration unless app proxy options are supplied; URLSession uses system settings by default and has a per-session proxy dictionary. Proxy authentication is fully surfaced by Dart and challenge-based on Apple, but is not a generic Cronet capability.
- HTTP/2/HTTP/3 enablement and negotiated-protocol reporting are not hard protocol requirements. Dart exposes ALPN only at the `SecureSocket` layer, Cronet/`HttpEngine` controls protocols at engine construction, and Apple’s `assumesHTTP3Capable` is explicitly a QUIC racing hint. Hard H2/H3 requirements must fail as unsupported unless an adapter can prove the protocol before dispatch.
- Cronet pauses at `onRedirectReceived`, but its public callback only lets the caller follow or cancel. Request headers are configured on `UrlRequest.Builder` before construction; the documented API provides no cross-origin redirect header replacement hook. The safe portable behavior is to cancel a cross-origin redirect when sensitive headers are present, unless the exact provider’s stripping behavior has been verified with a fixture.

## Verification status for the Android and Apple claims

The labels below distinguish what the official sources actually guarantee from adapter-level inference:

- **VERIFIED:** directly stated by an official API reference, platform guide, or current Chromium source.
- **VERIFIED LIMITATION:** the official public surface explicitly lacks or rejects the requested behavior.
- **UNCERTAIN / PROVIDER-DEPENDENT:** the API delegates behavior to a selected implementation, OS release, or system configuration and does not guarantee a portable result.
- **INFERENCE:** a conclusion from the documented public member list or lifecycle. It is useful for the AlphaX contract, but is not evidence about undocumented internal behavior.

## Dart `dart:io`

### Trust, anchors, and certificates

[`SecurityContext.defaultContext`](https://api.dart.dev/dart-io/SecurityContext/defaultContext.html) uses well-known trusted roots. The Dart documentation explicitly says that macOS, iOS, and Android use the platform trusted stores, while Linux and Windows use Mozilla’s root set. [`SecurityContext`](https://api.dart.dev/dart-io/SecurityContext-class.html) also documents certificate-chain/private-key methods and a minimum TLS protocol setting.

For custom anchors, [`SecurityContext`](https://api.dart.dev/dart-io/SecurityContext/SecurityContext.html) can be constructed with `withTrustedRoots: true`, then augmented with [`setTrustedCertificates`](https://api.dart.dev/dart-io/SecurityContext/setTrustedCertificatesBytes.html) (or the byte/string variant). Passing that context to the [`HttpClient`](https://api.dart.dev/dart-io/HttpClient-class.html) constructor gives a client-scoped policy. A context initialized without trusted roots is the custom-only shape; one initialized with trusted roots is the system-plus-custom shape. This is not a per-request flag.

`HttpClient.badCertificateCallback` is not pinning. The callback is invoked only when the peer certificate cannot be authenticated by the configured trusted roots; returning `true` accepts that otherwise bad certificate. A valid, trusted certificate with the wrong SPKI does not become a pin failure through this callback. The callback must remain null/rejecting for normal secure operation.

### SPKI pinning

[`X509Certificate`](https://api.dart.dev/dart-io/X509Certificate-class.html) exposes DER bytes and certificate metadata, but the public API does not expose the certificate’s public key or SPKI bytes. Therefore `dart:io` has no documented, first-class SPKI pin policy. Implementing it would require an additional DER/X.509 parser and a custom connection-validation path (or a separately verified native/provider facility). Any such path must retain ordinary trust and hostname validation, then compare the pin; it must not turn `badCertificateCallback` into a trust-all switch.

### mTLS

The [`HttpClient`](https://api.dart.dev/dart-io/HttpClient-class.html) documentation identifies `SecurityContext` as the place to configure a custom trusted CA or send a client certificate. The context’s `useCertificateChain*` and `usePrivateKey*` methods provide the certificate chain and private key. This is an `HttpClient`/context-level identity, not a request-independent portable identity abstraction. AlphaX should avoid putting raw private-key material in its pure-Dart public contract; use a securely supplied credential reference where possible, and document byte/key handling if it must be supported.

### Proxy and proxy authentication

[`HttpClient.findProxy`](https://api.dart.dev/dart-io/HttpClient/findProxy.html) accepts PAC-style results such as `DIRECT` and `PROXY host:port`, including ordered fallbacks. [`findProxyFromEnvironment`](https://api.dart.dev/dart-io/HttpClient/findProxyFromEnvironment.html) reads `http_proxy`, `https_proxy`, `no_proxy`, and their uppercase variants. The docs describe this as an environment helper, not an operating-system proxy/PAC integration. Setting `findProxy` to `null` gives direct connections; a callback returning `DIRECT` does the same for a resolved request.

For proxy challenges, [`authenticateProxy`](https://api.dart.dev/dart-io/HttpClient/authenticateProxy.html) receives the proxy host, port, scheme, and realm; credentials are installed with [`addProxyCredentials`](https://api.dart.dev/dart-io/HttpClient/addProxyCredentials.html). [`HttpClientCredentials`](https://api.dart.dev/dart-io/HttpClientCredentials-class.html) documents Basic, Bearer, and Digest credential forms. Credentials in an environment proxy URL are supported by the helper, but AlphaX diagnostics must redact the URL, username, password, and all authorization headers. The cited API surface documents HTTP proxy selection; it does not establish a portable SOCKS mapping.

### Protocol requirements

[`SecureSocket.connect`](https://api.dart.dev/dart-io/SecureSocket/connect.html) can offer an ALPN list such as `http/1.1` and `h2`; [`SecurityContext.setAlpnProtocols`](https://api.dart.dev/dart-io/SecurityContext/setAlpnProtocols.html) also configures ALPN, and [`SecureSocket.selectedProtocol`](https://api.dart.dev/dart-io/SecureSocket/selectedProtocol.html) reports the selected value. These are socket-level mechanisms. The public [`HttpClient`](https://api.dart.dev/dart-io/HttpClient-class.html) API does not expose an HTTP-version preference or a negotiated HTTP protocol property, and ALPN offering does not make the Dart `HttpClient` an HTTP/2 implementation.

The Dart adapter can honestly claim a protocol only from its implementation invariant (for example, an H1-only implementation), not from a post-response guess. A hard H2/H3 requirement is unsupported in the ordinary `HttpClient` path. Do not send a mutation and then reject it because the observed protocol was not the requested one.

## Android Cronet and `HttpEngine`

### Trust and pinning

**VERIFIED:** Android’s [Network Security Configuration](https://developer.android.com/privacy-and-security/security-config) is an app-manifest/declarative mechanism. It documents pre-installed system CAs as the default, custom `trust-anchors` that can either supplement or replace system anchors, and static SPKI pin sets. **VERIFIED LIMITATION:** its scope is app/domain configuration, not a per-request AlphaX policy, and the public [Cronet `CronetEngine.Builder`](https://developer.android.com/develop/connectivity/cronet/reference/org/chromium/net/CronetEngine.Builder?hl=en) and [platform `HttpEngine.Builder`](https://developer.android.com/reference/android/net/http/HttpEngine.Builder) pages do not document a runtime custom-root setter. **UNCERTAIN / PROVIDER-DEPENDENT:** whether a selected Cronet/`HttpEngine` provider consumes the app’s declarative configuration exactly as required by AlphaX. Treat dynamic per-client/per-request custom roots as unsupported unless the selected provider exposes and the adapter verifies an extension.

**VERIFIED:** Cronet and `HttpEngine` document first-class public-key pinning. [`CronetEngine.Builder.addPublicKeyPins`](https://developer.android.com/develop/connectivity/cronet/reference/org/chromium/net/CronetEngine.Builder?hl=en) and [`HttpEngine.Builder.addPublicKeyPins`](https://developer.android.com/reference/android/net/http/HttpEngine.Builder) specify SHA-256 hashes of DER-encoded ASN.1 `SubjectPublicKeyInfo`, with host, subdomain, and expiration controls. A chain succeeds only when a pinned key is present; a backup pin is recommended. **VERIFIED:** both builders expose a local-trust-anchor bypass control ([Cronet](https://developer.android.com/develop/connectivity/cronet/reference/org/chromium/net/CronetEngine.Builder?hl=en), [HttpEngine](https://developer.android.com/reference/android/net/http/HttpEngine.Builder)); `true` enables the bypass and `false` disables it. If pinning is a strict AlphaX policy, set bypass to false and test the chosen provider; otherwise a locally trusted interception certificate can bypass the pins. **UNCERTAIN / PROVIDER-DEPENDENT:** Chromium’s [current Cronet configuration source](https://chromium.googlesource.com/chromium/src/+/HEAD/components/cronet/url_request_context_config.h) records an enabled default for that internal configuration, but the default of every packaged provider is not a portable AlphaX guarantee. “Pinning configured” is therefore not by itself an honest statement of strict pinning.

The same conceptual controls are present on [`HttpEngine.Builder`](https://developer.android.com/reference/android/net/http/HttpEngine.Builder), but API level/provider availability differs. Build a separate engine for materially different engine-wide pin sets; do not imply that pins are request-local if the selected API is engine-scoped. Network Security Configuration debug overrides and pin expiration are deliberate exceptions in Android’s static model; they must not be silently enabled in a release security policy.

### mTLS

**VERIFIED LIMITATION:** the public [Cronet `UrlRequest.Callback`](https://developer.android.com/reference/android/net/http/UrlRequest.Callback) callback list contains redirect, response, read, success, cancellation, and failure callbacks, but no client-certificate challenge callback. The public [platform `UrlRequest.Builder`](https://developer.android.com/reference/android/net/http/UrlRequest.Builder) likewise documents request construction and headers, not a client identity selector. More strongly, the current [Chromium Cronet request source](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/cronet/cronet_url_request.cc) handles `OnCertificateRequested` by continuing with no certificate and states that Cronet does not support client certificates. **UNCERTAIN / PROVIDER-DEPENDENT:** a future or non-Cronet `HttpEngine` provider could add an extension, but it is not part of the public common API. Therefore mTLS is unsupported for the baseline Cronet/`HttpEngine` adapter. Do not substitute a WebView client-certificate API or claim provider behavior that is not part of the selected public provider contract.

### Proxy and proxy authentication

**VERIFIED:** the Cronet builder documents that system proxy configuration is handled internally when app proxy options are not supplied. [`CronetEngine.Builder.setProxyOptions`](https://developer.android.com/develop/connectivity/cronet/reference/org/chromium/net/CronetEngine.Builder?hl=en) says app proxy options override system configuration and warns that an older implementation may throw `UnsupportedOperationException`.

**VERIFIED:** the current platform and Cronet APIs are version-gated: [`ProxyOptions`](https://developer.android.com/reference/android/net/http/ProxyOptions), [`Cronet ProxyOptions`](https://developer.android.com/develop/connectivity/cronet/reference/org/chromium/net/ProxyOptions?hl=en), and [`Proxy`](https://developer.android.com/reference/android/net/http/Proxy) are API 37. `Proxy.createHttpProxy` documents HTTP/HTTPS proxy endpoints; `ProxyOptions.fromProxyList` documents ordered proxies and `ALL_PROXIES_FAILED_BEHAVIOR_ALLOW_DIRECT` or `DISALLOW_DIRECT`. The official page says the proxy-list constructor rejects an empty list, so there is no documented direct-only app configuration. “No app proxy” must not be mapped to “direct”; it means system/provider-managed proxy behavior. **UNCERTAIN / PROVIDER-DEPENDENT:** Cronet’s builder says older implementations may throw `UnsupportedOperationException` for `setProxyOptions`, so the selected provider and API level must be checked before claiming explicit proxy support.

**VERIFIED:** [`Proxy.HttpConnectCallback`](https://developer.android.com/reference/android/net/http/Proxy.HttpConnectCallback) can observe/control an HTTPS proxy CONNECT, and its [`Request.proceed`](https://developer.android.com/reference/android/net/http/Proxy.HttpConnectCallback.Request) can add extra headers to that CONNECT. The docs explicitly say those headers are not sent to requests through the resulting tunnel, and [`Proxy.createHttpProxy`](https://developer.android.com/reference/android/net/http/Proxy) says the callback is not called for an HTTP destination, where the full URI is sent to the proxy. **VERIFIED LIMITATION:** this is not a general proxy-auth challenge/retry API. **UNCERTAIN / PROVIDER-DEPENDENT:** system proxy authentication and any provider-specific auth behavior beyond the documented CONNECT hook. AlphaX should expose explicit proxy credentials on Android only if a concrete provider/API path handles the required scheme and both HTTP and HTTPS cases; otherwise return `unsupported` or a normalized proxy-auth failure rather than silently going direct.

### Protocol requirements

**VERIFIED:** Cronet documents native HTTP, HTTP/2, and HTTP/3 over QUIC support ([Cronet overview](https://developer.android.com/develop/connectivity/cronet)); both builders document engine-level HTTP/2 and QUIC toggles, and [`UrlResponseInfo.getNegotiatedProtocol`](https://developer.android.com/reference/android/net/http/UrlResponseInfo) reports the negotiated protocol after the response starts (or an empty string when unknown/plain HTTP/HTTPS). **VERIFIED LIMITATION:** there is no documented per-request “H2 only” or “H3 only” gate. **UNCERTAIN / PROVIDER-DEPENDENT:** disabling alternatives can express some engine-wide policies, but it does not create a universal pre-dispatch hard requirement across providers.

Use `getNegotiatedProtocol` for telemetry and for post-response checks where the request is safe to have sent. For a hard requirement on an unsafe mutation, reject before dispatch when the provider cannot guarantee it; do not send with a preference and label the result as enforced.

### Cross-origin redirect header control

[`UrlRequest.Callback.onRedirectReceived`](https://developer.android.com/reference/android/net/http/UrlRequest.Callback) is called before the response starts and pauses the request until the caller invokes `UrlRequest.followRedirect()` or cancels. [`UrlRequest.Builder.addHeader`](https://developer.android.com/reference/android/net/http/UrlRequest.Builder) configures headers while building the original request. The documented callback/builder surface contains no operation that replaces the pending redirected request or removes an individual header before `followRedirect()`.

The absence of a header-mutating redirect method is an API-surface conclusion, not a claim about every provider’s internal behavior. Cronet may apply internal redirect sanitization, but the cited public contract does not make that behavior an AlphaX-controlled guarantee. The minimum safe AlphaX policy is:

1. Inspect the redirect location and compare origins.
2. If the redirect is cross-origin and the request contains `Authorization`, `Cookie`, `Proxy-Authorization`, or another credential-bearing header, cancel it unless the exact provider version has a tested, documented stripping guarantee.
3. Do not solve this by rebuilding and replaying a mutation automatically; that changes retry semantics and can duplicate side effects.

## Apple `URLSession` and Security

### Trust, anchors, and SPKI pinning

**VERIFIED:** URLSession’s default server-trust handling is the platform baseline. Apple’s [manual server-trust authentication](https://developer.apple.com/documentation/foundation/performing-manual-server-trust-authentication) documentation describes using the URLSession delegate challenge when an app needs to tighten trust, including pinning or custom certificates. It also says to evaluate the supplied `SecTrust` and use a trust credential only after successful evaluation; invalid trust should be cancelled. ATS remains in force for protected domains and can be tightened, not loosened.

**VERIFIED:** for custom anchors, [`SecTrustSetAnchorCertificates`](https://developer.apple.com/documentation/security/configuring-a-trust) adds the application’s anchors to the referenced trust object. [`SecTrustSetAnchorCertificatesOnly`](https://developer.apple.com/documentation/security/sectrustsetanchorcertificatesonly) controls whether the normal built-in anchors remain eligible: `false` is system-plus-custom, while `true` is custom-only. Finish with [`SecTrustEvaluateWithError`](https://developer.apple.com/documentation/security/sectrustevaluatewitherror). These calls affect only the referenced trust object, not a global URLSession trust-all switch.

**VERIFIED:** Apple has no single URLSession SPKI-pin property, but manual pinning can use the server certificate chain and public key. Apple’s manual-trust article explicitly describes comparing a certificate/public key or its hash and recommends a set of keys/CA keys for rotation. [`SecCertificateCopyKey`](https://developer.apple.com/documentation/security/seccertificatecopykey) obtains a `SecKey`, and [`SecKeyCopyExternalRepresentation`](https://developer.apple.com/documentation/security/seckeycopyexternalrepresentation) obtains an external key representation when the key is exportable. **UNCERTAIN / IMPLEMENTATION-DEPENDENT:** the latter is not automatically DER `SubjectPublicKeyInfo`—Apple documents algorithm-specific external forms such as RSA PKCS#1 and EC ANSI X9.63—so an adapter that promises the same SPKI SHA-256 semantics as Cronet must DER-encode the SPKI structure before hashing, or explicitly use a different pin representation. If the key is non-exportable, fail the pin check rather than weakening trust. Pin after normal trust evaluation, accept a set of backup keys, and cancel on mismatch.

### mTLS

**VERIFIED:** the [URLSession delegate challenge API](https://developer.apple.com/documentation/foundation/urlsessiondelegate) documents session-level handling for `NSURLAuthenticationMethodClientCertificate`; the relevant methods are also listed with Apple’s [authentication-method constants](https://developer.apple.com/documentation/foundation/nsurlprotectionspace-authentication-method-constants). The response is a [`URLCredential`](https://developer.apple.com/documentation/foundation/urlcredential) created from a `SecIdentity` and optional intermediate certificates using Apple’s [`init(identity:certificates:persistence:)`](https://developer.apple.com/documentation/foundation/urlcredential/init%28identity%3Acertificates%3Apersistence%3A%29). Apple says the persistence parameter is ignored for this initializer and recommends `.forSession`; TLS credentials are not permanently stored by `URLCredentialStorage` ([credential persistence](https://developer.apple.com/documentation/foundation/urlcredential/persistence-swift.enum?language=objc)). **UNCERTAIN / IMPLEMENTATION-DEPENDENT:** the app still has to supply/select the actual keychain `SecIdentity` and handle missing identities and acceptable issuer names.

The native adapter can therefore support mTLS, but the pure-Dart public contract should pass a keychain identity reference/alias or opaque native credential handle rather than raw private-key objects. The adapter must define identity selection and missing-identity errors explicitly.

### Proxy and proxy authentication

**VERIFIED:** Apple’s [URLSession](https://developer.apple.com/documentation/foundation/urlsession) documentation says the system URL loading stack supports system-configured proxy servers and SOCKS gateways. [`URLSessionConfiguration.connectionProxyDictionary`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/connectionproxydictionary) provides a legacy per-session proxy dictionary; `nil` means use the default system settings. Apple’s newer [`proxyConfigurations`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/proxyconfigurations) property also defaults to system settings when empty. The [global proxy constants](https://developer.apple.com/documentation/cfnetwork/global-proxy-settings-constants) document HTTP/HTTPS/SOCKS/PAC host, port, enable, and exception keys, and [CFNetwork proxy types](https://developer.apple.com/documentation/cfnetwork/proxy-types) include `kCFProxyTypeNone`, HTTP, HTTPS, SOCKS, and PAC. Thus explicit proxy and direct policies are representable through the CFNetwork configuration path. **UNCERTAIN / OS-VERSION-DEPENDENT:** `connectionProxyDictionary` is legacy and Apple says to prefer `proxyConfigurations`; the adapter must verify the resulting route rather than infer it from a nil/empty configuration.

**VERIFIED:** [`URLProtectionSpace`](https://developer.apple.com/documentation/foundation/urlprotectionspace) identifies proxy protection spaces, including proxy type, host, port, and realm. Apple’s [authentication-challenge guidance](https://developer.apple.com/documentation/foundation/handling-an-authentication-challenge) permits task/session delegates to answer with a `URLCredential` for supported schemes. The adapter should check `protectionSpace.isProxy`, never put proxy credentials in an origin `Authorization` header, use session-scoped credential lifetime, and treat unsupported proxy schemes or repeated challenges as explicit failures. **UNCERTAIN / PROVIDER-DEPENDENT:** URLSession owns the CONNECT/proxy exchange, and the public API does not promise that every proxy authentication scheme is manually controllable or that a credential will be challenged in the same way on every OS release.

### Protocol requirements

**VERIFIED:** Apple documents that [URLSession](https://developer.apple.com/documentation/foundation/urlsession) supports HTTP/1.1, HTTP/2, and HTTP/3, and [`URLSessionTaskTransactionMetrics.networkProtocolName`](https://developer.apple.com/documentation/foundation/urlsessiontasktransactionmetrics/networkprotocolname?language=objc) reports the actual protocol used (including the tunneled protocol when a proxy is involved). [`URLRequest.assumesHTTP3Capable`](https://developer.apple.com/documentation/foundation/urlrequest/assumeshttp3capable) enables QUIC racing when the endpoint is known to support HTTP/3; its default is false. Apple’s [HTTP/3 technical note](https://developer.apple.com/documentation/technotes/tn3102-http3-in-your-app) explicitly describes fallback to `h2` or `http1.1` when HTTP/3 is unavailable. **VERIFIED LIMITATION:** this is a hint/fallback model, not an H3-only requirement.

**VERIFIED LIMITATION:** there is no documented per-request hard H2/H3 requirement in this surface. Treat `networkProtocolName` as telemetry or a post-response check for safe requests, not as pre-dispatch enforcement. **UNCERTAIN / OS-VERSION-DEPENDENT:** a future provider/API could add a hard requirement, but the baseline URLSession contract cannot honestly advertise one today.

## Actionable AlphaX contract decisions

1. Keep the public capability vocabulary separate from implementation preferences. “Prefer H2/H3” can map to platform enablement/hints; “require H2/H3” must be rejected before dispatch on these baseline adapters unless a provider proves enforcement.
2. Model trust anchors as scoped configuration: Dart `HttpClient`/`SecurityContext`, Apple trust challenge, and Android app/domain configuration. Do not expose Android dynamic custom roots as if they were equivalent to Dart or Apple.
3. Define pinning as SPKI SHA-256 over DER `SubjectPublicKeyInfo`, with multiple pins and a strict mismatch result. Cronet can do this natively; Apple requires careful DER encoding; Dart is unsupported in the baseline `dart:io` adapter.
4. Keep mTLS identity material native/secure. Dart and Apple can support it; public Cronet/`HttpEngine` cannot currently select a client identity. Missing identity, handshake failure, and unsupported transport capability should remain distinguishable.
5. Separate proxy mode from proxy authentication. “System proxy” is provider/platform managed; “direct” must be forced, not inferred; “explicit proxy” needs a fail-closed option. Never silently fall back to direct when a proxy or proxy credential is required.
6. For Cronet redirects, cancel sensitive cross-origin redirects by default. A callback that can pause/follow is not header control. Any relaxation requires provider-version evidence and a regression fixture covering `Authorization`, cookies, proxy headers, redirect origin, and request method/body.
7. Keep diagnostics safe: redact proxy URLs/credentials, client-key identifiers where sensitive, certificate material, request bodies, and authorization headers. A policy failure should identify the normalized capability/error class without logging secrets.
